# 计划：TunnelPad 无人值守 ECS 公网 IP 漂移同步与断线恢复

> 本计划是对已完成的[ECS 动态 SSH 公网 IP 同步](ecs-dynamic-ssh-ip.md)的后续能力补充，不重开其历史阶段，也不把本次真实故障误记为原计划已验收。

依赖关系：复用[开机自启与隧道自动恢复](tunnelpad-launch-autostart.md)的启动队列和退避边界、[无人值守 SSH 异常恢复与孤儿清理](tunnelpad-unattended-ssh-recovery-and-orphan-cleanup.md)的进程树收敛，以及[ECS 动态 SSH 公网 IP 同步](ecs-dynamic-ssh-ip.md)的规则事务。

## 背景与已确认事实

2026-09-19 对 `motorcycle-local-docker` 的真实只读诊断确认：本机公网出口已变化，ECS 中唯一一条 `tunnelpad-dynamic-ssh-managed` 入方向 TCP `22/22` `/32` 规则仍为旧来源；该规则创建时间为 2026-09-04。SSH 在握手阶段被远端关闭，launchd 以 10 秒节流持续重启代理/SSH，`last exit code=255`。

当前同步能力存在三个边界：

1. `update-ecs-ssh-ip` 的无参数模式具备“探测 → 读取 → 新增当前规则 → 确认 → 删除旧规则”的真实同步逻辑。
2. App 的启动/显式 start/restart/健康恢复前置会调用无参数模式，但 launchd 的 `KeepAlive` 自行重启 SSH 时不会再次调用 ECS 前置。
3. `--check` 只检查受管规则数量，没有比较 `SourceCidrIp` 与当前探测结果，因此旧规则也会被错误报告为 `synchronized`。该问题位于 `rust/tunnelpad-core/src/preflight/transaction.rs` 的 check 分支。

本次故障的直接原因不是同步 API 已执行但写入失败，而是公网 IP 漂移后没有重新进入同步前置；错误的 `--check` 结果又掩盖了规则漂移。

真实运行复验又发现第二个独立问题：旧 SSH 会话遗留在 ECS 上继续占用 `127.0.0.1:18080`，新 SSH 因 `ExitOnForwardFailure` 退出；launchd 的短暂 `running` 状态曾被错误当成恢复成功，导致恢复任务每 2 秒重复触发。该旧会话已按精确受管 PID 清理，代码补充了“启动后稳定采样”和后续退避。

## 目标

- 修正只读检查契约：规则来源不是当前公网 `/32` 时必须明确返回漂移，不得返回 `synchronized`，且不得写云端。
- 在 TunnelPad App 常驻的无人值守边界内，检测网络/IP 漂移或 launchd SSH 快速失败，先让当前作业进入 `notLoaded`，再执行一次受控 ECS 前置和 SSH 重启。
- 防止 launchd 在前置同步期间以 `KeepAlive` 无限重启；同步失败时保留恢复意图，以有上限的重试间隔持续恢复。冷却到期必须自动复核，不因失败次数耗尽永久停止。
- 不把 launchd 短暂 `running` 或连续三次相同代理 PID 当作 SSH 已恢复；连接/转发成功证据及稳定窗口通过后才清零失败历史。具体证据采集方式由修复设计落实，历史三次 PID 自验不再作为新目标的完成判据。
- 保持现有受管规则安全边界：只管理精确描述、协议、端口、方向、策略和 `intranet` 元组；不触碰其他安全组规则。
- 保证旧代理/SSH 已收敛后才恢复新实例，不产生孤儿 SSH 或并行连接。

## 持续恢复硬性契约

2026-09-19 用户明确要求：不能出现重连失败若干次后自行停止、必须人工点击启动的情况。本节是修复后的强制要求，不代表当前实现已满足，也不解除现有独立复核失败。

- 对已取得自动恢复资格、且未被用户取消的隧道，失败不是终态。每次失败必须保留恢复意图，并登记下一次重试或安全复核；不能只保存失败计数，却没有任何后续调度。
- 普通网络、IP 漂移、服务暂时不可用、可恢复的转发冲突等故障，首次恢复立即进入受控流程，后续按有上限的间隔退避。失败次数、单轮超时、一次任务抛错或冷却阈值均不得耗尽整个恢复流程；多个冷却周期后仍必须继续。
- 下一次恢复由保留的待恢复状态和到期调度驱动，不依赖已停止 SSH 再次退出、PID 再次变化、业务探针存在或用户操作。即使作业已经 `notLoaded`，外部条件恢复后也必须自动重新执行完整前置并连接。
- 凭据、权限、配置错误或资源归属不明时，暂停的是危险云写/进程信号/启动，不是监督任务。继续限频执行适用的安全复核；确认条件恢复后自动续跑。不得自行生成有效凭据、扩大权限或清理未知进程来冒充自动恢复；外部问题未消除时持续显示阻塞原因。
- 先确认旧实例安全收敛，再等待下一次连接尝试；身份无法证明时保留监督和诊断，禁止发信号或新建并行实例。重试不能绕过 ECS 前置，也不能恢复独立的 launchd SSH 自启动通路。
- 用户明确停止、删除隧道、取消相应自动恢复意图或主动退出 App 才能取消对应恢复资格；备注/显示名称变化不能取消资格，也不能复活已被手动停止的项。范围仍是用户已登录、App 常驻，不扩展为登录前或 App 不运行时的系统服务。
- 状态与带时间日志须区分“连接中、等待重试、等待安全条件、已连接、用户停止”，可查最后失败原因和下一次动作；不能静默从失败变为无任务的停止状态。重复故障日志仍限频。

此处的失败重试/安全复核仅作用于待恢复任务，不是重新引入面向健康连接的常驻五分钟 IP 轮询。永久错误未消除时不能保证连接成功，但系统不得自行放弃监督；可恢复条件消除后的自动续跑必须由测试证明。

## 非目标

- 不在日志代理内直接调用 ECS API；代理只负责 SSH 子进程和日志生命周期。
- 不扩大 SSH 来源、不创建 `0.0.0.0/0`、不管理非 TunnelPad 规则，不保存凭证、私钥或原始公网 IP。
- 不把 Workbench 改造成端口转发，不改变 `18080` 的现有 SSH 转发语义。
- 不要求 TunnelPad App 退出后仍维持隧道；当前 App 退出会停止受管隧道。若要实现“App 不运行但仍自动同步/恢复”，另立系统级 launchd 前置计划。

## 推荐修复方案

### 1. 先修正同步检查语义

在 `--check` 分支中：

- 双端点探测并严格校验公网 IPv4；
- 读取受管规则并拒绝零条以外的歧义；
- 唯一受管规则的来源等于当前 `<ip>/32` 时返回 `synchronized`；
- 来源不等时返回稳定的 `ip_drift` 结果，使用现有错误退出通道，绝不调用 `AuthorizeSecurityGroup` 或 `RevokeSecurityGroup`；
- 保留待处理 journal 的一致性校验。

无参数模式继续沿用既有“先新增并确认，再按旧规则 ID 删除”的事务流程。`--check` 不能被当作同步成功的替代品。

### 2. 增加 App 层公网 IP 漂移协调器

由 Swift `TunnelManager`/专用协调器持有单隧道状态和代次，不把 ECS 逻辑复制到 Rust Core：

- App 启动时做一次正确的 `--check`；
- 运行期间不依赖常驻 5 分钟轮询；断开或 launchd 异常退出时由生命周期恢复门触发前置检查，启动交接保留一次性复核；
- 发现 `ip_drift` 时，对受影响的 SSH 隧道串行执行 `stop/bootout → 确认 notLoaded → 无参数 ECS 同步 → bootstrap/start → 状态与探针确认`；
- 多条 SSH 隧道共享同一 ECS 资源时只允许一个同步事务，其他隧道等待同一结果，不重复写安全组；
- 端点不一致、出口不可确认、权限失败、锁冲突或云端状态歧义时 fail-closed，不启动新 SSH。

公网 IP 变化本身不要求立即改云端规则；下一次连接建立前必须重新做前置检查。这样即使代理、VPN 或路由变化没有产生明确的接口事件，也不会让旧规则被直接拿来重连。

### 3. 把 launchd 快速失败纳入同一恢复门

对当前这种 `Connection closed`/退出码 `255` 的情况：

- 识别同一 label 在短窗口内的连续退出/`spawn scheduled` ↔ `running` 抖动；
- 达到阈值后先由 Rust owner bootout 当前 label，并确认 `notLoaded`、代理/SSH 进程组和转发端口均已收敛；
- 再运行 `--check`。若为 `ip_drift`，执行一次无参数同步；若规则已最新，则不重复写 ECS；
- 成功后只 bootstrap 一次并交给健康监测；失败则按有界退避暂停，禁止 KeepAlive 继续制造 10 秒错误风暴；
- 每次恢复记录时间、阶段、脱敏结果和重试次数，日志不得写入原始 IP、凭证或私钥。

不要把 ECS 前置塞进 `tunnelpad-log-proxy`：那会让底层代理承担云端权限，并在 KeepAlive 重启风暴中重复调用云 API。

### 4. 保留并增强可观测性

至少区分以下事件：`ip_probe`、`ip_drift`、`ecs_sync_started`、`ecs_sync_succeeded`、`ecs_sync_failed`、`launchd_churn_detected`、`quiesced`、`ssh_restarted`。每条带本地时间和脱敏资源标识；正常重复事件按结果和时间窗口压缩。

### 本次阶段 1 实现取舍

- `--check` 已改为真正比较当前探测到的公网 `/32`，漂移返回稳定的 `ip_drift` 结果且不调用云端写接口。
- App 侧原先接入的启动后低频漂移复查已确认不适合作为无人值守主路径：它会让 launchd 先拿旧规则反复重连，再等待最多 5 分钟才发现漂移。本轮删除常驻 5 分钟轮询；启动交接保留一次性前置复核，运行期间由 launchd 生命周期异常直接进入 bootout-first、前置同步和启动恢复链。
- 为避免扩大共享健康状态机的影响面，没有直接修改 `HealthRecoveryState`，而是在 `TunnelManager` 外围复用其现有的三次失败、退避和冷却语义。
- 真实 `18080` 冲突暴露了“启动返回 running 即清零计数”的缺口；本阶段在 `TunnelManager` 外围增加稳定性观察门，并让 direct launchd failure 的后续尝试使用健康恢复退避，不修改共享 `HealthRecoveryState` 契约。
- 本阶段暂不引入新的 `NWPathMonitor` 事件源；连接建立前的前置门和 launchd 异常触发已覆盖当前故障，网络事件不再通过另一个常驻轮询间接驱动恢复。

## 失败、回滚与安全边界

- 任何 IP 来源不一致、目标安全组歧义、凭证/权限异常、状态未知、旧进程未收敛或网络路径无法确认时，保持 fail-closed。
- 规则轮换继续由既有事务保证：新增未确认不删旧规则；撤销失败保留新旧规则并报告。
- 恢复协调器失败时只 bootout 当前 TunnelPad label，不清理未知 SSH，不触碰非目标隧道。
- 回滚代码前先停止漂移协调器、确认目标 label 和进程组收敛；回滚 App 不自动删除云端受管规则，云端规则按只读核对后再决定是否人工处理。
- 阶段 2 真实验收若失败，停止扩大范围，保留 Workbench/现有生产 SSH 恢复路径，不继续反复写 ECS。

## 独立审核结论（2026-09-19）

独立子任务 Lorentz 对当前工作集执行了只读审核，未修改代码、未写入云端、未启动或停止 App。结论为“不通过”：未发现 P0，但以下 P1 缺陷必须先修复并重新独立复核。

1. `rust/tunnelpad-core/src/preflight/transaction.rs:375-388` 在存在 pending journal 时仅校验 journal 结构并返回成功，没有再次比较当前探测 IP、确认云端最终规则唯一且不残留旧 `/32`；`Sources/TunnelPadCore/ECSPreStart.swift:290-295` 会把该结果作为同步完成，可能在 IP 已从 A 变为 B 时误报 `synchronized`。
2. `Sources/TunnelPadCore/TunnelManager.swift:1058-1095` 与 `Sources/TunnelPadCore/LaunchRecoveryCoordinator.swift:100-123` 的自动恢复路径逐隧道直接调用 `checkAsync`，没有复用启动路径的 ECS 资源串行化/等待队列；共享 ECS 的多个隧道同时恢复时可能得到 `lock_busy`，从而漏掉应有的等待与重试。
3. `rust/tunnelpad-core/src/bin/tunnelpad-log-proxy.rs:152-160,202-220` 在收到停止信号后，若子进程延迟退出，仍可能先把 `Interrupted` 记为失败；现有测试未覆盖延迟或忽略 `SIGTERM` 的子进程，正常停止仍有误报风险。
4. 阶段 2 所需的真实漂移注入、长时无人值守、延迟停止和孤儿反证证据尚未形成；独立审核认为现有短时/受控运行证据不足以支持高影响完成结论。

另有 P2 风险：`--check` 对已存在规则主要比较来源 `/32`，没有完整证明优先级、协议、目的端口等规则属性；自动恢复的全链路事件时序和长时间退避/冷却也缺少直接证据。

已确认仍然成立的部分：常驻 5 分钟 IP 轮询已删除；断线恢复的设计顺序在无上述边界条件时是“先收敛、检查/同步、再启动”；稳定采样和失败退避存在。但这些不足以抵消上述 P1 阻塞项。
